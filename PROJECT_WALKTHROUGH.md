## 1. Course Introduction

### Unit 1 — Building a RAG System

Retrieval-Augmented Generation (RAG) is the architecture behind AI systems
that answer questions about specific material instead of from a model's own
memory: the system retrieves relevant source text *before* the model writes
anything, which is what keeps answers grounded instead of confidently
invented. Unit 1 has students build such a system — "The Unofficial Guide," a
searchable knowledge base over informal, real campus information — one
pipeline stage at a time, replacing a deliberately plain starter piece by
piece so the effect of each decision is visible on its own.

The unit's own framing is that it trains a specific, interview-relevant skill:
not "I built a RAG system," but "I can say how I knew it worked." Unit 1's
learning objectives are to build a document pipeline (load, clean, chunk,
embed), query a vector store and judge the results, generate grounded answers
that name their sources, decide in code when nothing is worth answering from,
and write acceptance criteria specific enough for someone else to check.

### Unit 2 — Testing a RAG System

Unit 2 reuses the same repository and system — nothing new gets built — to
test the five acceptance criteria written in Unit 1 against real, repeated
runs. Each criterion is run three times (a single run "tells you almost
nothing"), called MET or MISSED against the target written *before* any
result existed, diagnosed by pipeline stage when missed, and followed by
exactly one measured fix.

The unit is explicitly structured so that missing targets costs nothing and
loosening a target after the fact costs the point — "a criterion loosened
until it passes leaves you nothing to diagnose." Its learning objectives are
to test with repeated trials rather than a single lucky run, judge a
criterion honestly including when it's close, trace a failure to the pipeline
stage that caused it, distinguish a criterion that was missed from one that
was unmeasurable, and make one change, measure it, and report the result
either way — including if it didn't help.

## 2. Project Title, Problem, Goals, and Architecture

### The Unofficial Guide

**What it does.** A command-line RAG system that answers practical questions
about student life by retrieving from a chosen corpus of short, informal
documents and generating an answer grounded only in what was retrieved, with
every answer naming its source file. The corpus in active use is
`campus_life` — 88 short documents (graduation requirements, health center
hours, on-campus job limits, course workloads, dining hall costs, housing
rules) — confirmed as the live default via `config.py:23` and via running
`python app.py corpora` (Section 4).

**The problem it solves.** A language model answering from its own training
data will confidently invent plausible-sounding but wrong specifics (exact
hours, exact dollar amounts, exact course names) that don't exist in any real
campus document. This system retrieves the actual source text first, refuses
to answer when nothing retrieved is close enough to the question (the
relevance gate), and otherwise restricts generation to only the retrieved
text, naming the file it came from.

**Goals**, as embodied by the five acceptance criteria in `criteria.md`
(reproduced in full in Section 6, Unit 1 → Milestone 2):

1. Retrieval surfaces the answer-bearing chunk for most test questions.
2. Every answer names at least one source document.
3. The relevance gate correctly refuses most out-of-corpus questions.
4. Most sampled chunks are complete sentences, not mid-sentence fragments.
5. A fixed, author-chosen set of five in-scope test questions all pass.

## 3. Glossary

| Term | What it means | Where it shows up |
|---|---|---|
| Chunk | A small piece of one document; the system searches chunks, not whole files | `chunker.py::Chunk` dataclass (`text`, `source`, `index`, `produced_by`) |
| Overlap | Characters shared between neighbouring chunks, so a sentence doesn't get cut in half | `config.CHUNK_OVERLAP` (800-character fallback chunker only; the hand-rolled and LangChain chunkers described in Section 6 use 0 and 50 respectively) |
| Embedding | A list of numbers standing for a chunk's meaning; similar meaning, similar numbers | `store.py::embed()`, via Chroma's bundled ONNX build of `all-MiniLM-L6-v2` (384 dimensions) |
| Vector store | The database holding embeddings and finding close matches quickly | `store.py`, backed by `chromadb.PersistentClient` at `chroma_db/` |
| Retrieval | Handing the store a question and getting back the nearest chunks | `store.py::search()` |
| Top-k | How many chunks come back per question | `config.TOP_K = 5` |
| Distance | How far a chunk is from the question in meaning; lower is better | `store.Result.distance`, cosine distance (`store.py:162`, explicit `hnsw:space: cosine`) |
| Grounding | Making the model answer only from retrieved documents, never from its own training data | `generate.GROUNDING_INSTRUCTION`, the system prompt sent with every generation call |
| Relevance gate | A pre-generation check that refuses to answer when nothing retrieved is close enough | `gate.py::check()`, compares `best_distance` against `config.THRESHOLD` |
| Relevance cutoff / threshold | The distance value the gate refuses above | `config.THRESHOLD = 0.6` |
| Produced by | A tag on every `Chunk` naming the exact function that created it, for citing in writeups | `Chunk.produced_by` |
| Variant | A label letting the same corpus be indexed more than one way at once, without deleting either | `store.collection_name(..., variant=...)`; used for Unit 2's before/after comparisons |
| Acceptance criterion | A target specific enough that a person could plainly check it, written before any results exist | `criteria.md` |
| Gate evidence | The record of how the relevance gate handled the `OUT_OF_SCOPE` questions, written into every run log | `run_eval.py::check_out_of_scope()` |
| Run log | The per-question, per-run pass/fail table `run_eval.py` writes to `results/` | `results/run_<timestamp>_<label>.md` |
| Judge | The function deciding whether one generated answer counts as correct | `scorer.py::judge()` — see Section 5, Finding 4 for what this does and does not cover |

Milestones below introduce further project-specific terms by name only
(definitions are not duplicated into their entries) — see each milestone's
"Terms introduced" line, defined above.

## 5. Findings and Lessons Learned

Each finding states the fact and the real evidence first; prose explanation
is added only where the mechanism isn't obvious from the evidence alone.

**Finding 1 — The Sample Chunks in `README.md` (Unit 1) document a different
corpus than the one the rest of the project uses.**
`corpora/README.md:70-71` states outright: "Below is the exact output of
`python app.py --corpus advice_threads chunks -n 5`." The five chunks pasted
into `README.md`'s own Sample Chunks section (`thread_bike_commute.txt`,
`thread_first_gen.txt`, `thread_laptop_specs.txt`,
`thread_office_hours_etiquette.txt`, `thread_roommate_conflict.txt`) are all
`advice_threads` files. Every other part of the project — `README.md`'s own
header comment (`CORPUS: campus_life`), `config.py`'s default (`campus_life`,
confirmed live via `python app.py corpora`, Section 4), `criteria.md`, and
all five of `questions.py`'s `QUESTIONS` — is written against `campus_life`.
Mechanism: the student ran the new chunker against `advice_threads` while
developing it in Milestone 3, captured that output into both
`corpora/README.md` and `README.md`, then settled on `campus_life` as the
project's actual corpus for Milestones 2, 4, and all of Unit 2, without
regenerating the Sample Chunks section against it.

**Finding 2 — The chunker function actually wired into the pipeline today
cannot run, independent of any missing package.**
Live run, 2026-10-31: `python app.py index` on `campus_life` fails with
`ModuleNotFoundError: No module named 'langchain_text_splitters'` (not listed
in `requirements.txt`; see `ENVIRONMENT_SETUP.md` §3). After installing it,
the same command instead fails with `AttributeError: 'Document' object has no
attribute 'page_content'`, raised at
`.venv/Lib/site-packages/langchain_text_splitters/base.py:157` because
`chunker.py:153` passes this project's own `ingest.Document` (fields:
`source`, `text`) into LangChain's `RecursiveCharacterTextSplitter`, which
expects *its own* `Document` type (`page_content`, `metadata`). This is not a
missing-dependency problem at that point; it is a real type mismatch between
this repo's data model and the library the active code calls. Mechanism,
pinned to a commit: commit `e302357` (2026-09-28, "Expanded chunker.py and
scorer.py function approaches/methods & execution notes") is where this
happened — verified via `git diff eebfccc e302357 -- chunker.py`. That commit
wrapped the previously-working, previously-active hand-rolled paragraph
splitter (the one that actually produced every Sample Chunk and every Unit 1
result in this document) inside a triple-quoted string, turning it into dead
code, and replaced it with the LangChain call shown above as the new, active
`split_documents` body.

**Finding 3 — The documented "fallback" function is also broken, by a typo
introduced in the same commit as Finding 2.**
`chunker.py:73` constructs `Chunk(text=piece, somurce=doc.source, index=index,
produced_by=...)`. `Chunk` (`chunker.py:32-43`) has a field named `source`,
not `somurce`. Live run, 2026-10-31:
`TypeError: Chunk.__init__() got an unexpected keyword argument 'somurce'.
Did you mean 'source'?` `git show e302357:chunker.py` and
`git show eebfccc:chunker.py` confirm this: the line read `source=doc.source`
before `e302357` and `somurce=doc.source` after it. `chunker.py`'s own
docstring calls `fallback_split` "the stop rule" for Milestone 3 — "If you get
stuck for 30 minutes... switch back to it" — and that stop rule has not run
successfully since 2026-09-28.

**Finding 4 — `scorer.py::retrieval_hits` is never called by any code in this
repository.**
`grep -rn "retrieval_hits"` across the repository returns exactly one line:
its own definition at `scorer.py:91`. `run_eval.py:115` calls only
`judge(question, expects, answer, results)`. This means the single per-run
pass/fail mark every question gets in a run log comes entirely from
`judge()` — the same function, run the same way, regardless of which
criterion a reader later maps that output to.

**Finding 5 — `README.md`'s own Unit 2 "Run Log — Before" table contradicts
the raw evidence pasted directly beneath it.**
`README.md:213` states Criterion 1 ("Retrieved chunk contains the answer") is
**MET**, 5/5, on all three runs. The "Real system output for Criterion 1"
section immediately below it (`README.md:229-250`) — which matches
`results/run_2026-09-28_1724_before.md` verbatim — shows **`fail`** for all 5
questions on all 3 runs. This is not two different measurements disagreeing;
per Finding 4, both the Criterion 1 evidence and the Criterion 5 evidence
shown in the same README are the *same* `judge()` output, since `run_eval.py`
has no separate check for "the retrieved chunk contains the answer." The MET
verdict for Criterion 1 rests on the student's own manual read of which
*source files* retrieval surfaced ("every in-scope query retrieved its
corresponding ground-truth text document," `README.md:220`) — a real and
separately defensible observation — stated beside automated output that, read
at face value, says the opposite. The README does not flag this gap itself.

**Finding 6 — Two packages the active chunker and the Unit 2 scorer import
are not listed in `requirements.txt`.**
`chunker.py` imports `langchain_text_splitters`; `scorer.py` imports
`rapidfuzz`. Neither appears anywhere in the project's 31-line
`requirements.txt`. Confirmed live: `pip show langchain-text-splitters
rapidfuzz` against this repo's own `.venv` returned `WARNING: Package(s) not
found` before this audit installed them. `python test.py` passing 10/10
(Section 4) does not catch this, because `test.py` only imports the packages
`requirements.txt` pins — it never imports `chunker.py` or `scorer.py`.

**Finding 7 — The second committed run-log file is mislabeled: its name and
heading say "before," but its data is the Unit 2 "after" run.**
`results/run_2026-09-29_1810_before.md` opens with `# Run log — before`. Its
per-question table (Q1 fail/fail/fail, Q2 fail/pass/fail, Q3 pass/pass/pass,
Q4 fail/pass/fail, Q5 pass/pass/pass) aggregates to 2/5, 4/5, 2/5 across its
three runs — exactly the numbers `README.md:480` reports under "Run Log —
After." The real "before" run (0/5, 0/5, 0/5, matching `README.md:217`) is
correctly preserved in `results/run_2026-09-28_1724_before.md`. Mechanism:
`run_eval.py`'s `--label` flag names the output file (`run_eval.py:182`); the
student re-ran `run_eval.py --label before` instead of `--label after` when
re-testing with the fixed `scorer.py`. A third file,
`run_2026-09-29_1738_before.md`, was created by commit `61a7a89` and deleted
by the very next commit, `cfdabd9` ("file cleanup") — an intermediate attempt
superseded by the 18:10 run, not evidence of a different result being hidden
(its 193-line removal exactly matches its 193-line addition one commit
earlier, confirmed via `git show --numstat` on both commits).

**Finding 8 — Local, uncommitted Chroma data on disk predates the pinned
`chromadb` version and cannot be listed by it.**
`chroma_db/` is correctly gitignored (`.gitignore` line: `chroma_db/`) and
not part of the repository's history. As found on this machine on
2026-10-31, calling `chromadb.PersistentClient(...).list_collections()`
against it raises `KeyError: '_type'` while parsing a stored collection
config, with `chromadb==0.6.3` installed (matching the `>=0.6,<0.7` pin).
This is local machine state, not a defect in committed code — full detail and
the practical fix are in `ENVIRONMENT_SETUP.md` §5.

### Lessons

1. **A passing `test.py` is a floor, not a guarantee.** It verifies the
   packages `requirements.txt` pins, the key, and one live model call — it
   never imports `chunker.py` or `scorer.py`, so a break in either (Findings
   2, 3, 6) is invisible to it. Reason: `test.py`'s own design only walks the
   dependency list it knows about.
2. **Commenting out a working function to try a new one, in the same file,
   without deleting the old one, is how dead code and live code silently swap
   roles.** Reason: Finding 2 — the hand-rolled splitter that produced every
   real result in this document is one `#` away from running again, but
   nothing marks which of the three bodies in `chunker.py` is actually live
   except which one isn't wrapped in triple quotes.
3. **A verdict and the evidence under it can quietly diverge once they're
   produced by different processes — one automated, one by eye.** Reason:
   Finding 5 — "MET" came from reading source filenames by hand; "fail" came
   from `judge()`. Both are real observations about the same run; neither
   alone is the full picture, and the README never says so.
4. **A one-word typo in a keyword argument fails loudly (`TypeError`), which
   is the easy case.** Reason: Finding 3 is trivial to fix once noticed
   because Python refuses to run it at all — contrast with Finding 2, where
   the code runs for a while (loads 88 documents) before failing, and would
   silently produce the *wrong* chunks rather than an error if the type
   mismatch happened to be compatible.
5. **A `--label` flag only records what you type, not what actually
   happened.** Reason: Finding 7 — the "after" run has real, correct,
   verifiable data; it is simply filed under the wrong name because the
   command line doesn't know what the data represents, only what string
   followed `--label`.
6. **An ad hoc `pip install` during development that never gets added to
   `requirements.txt` becomes invisible the next time the environment is
   rebuilt from scratch.** Reason: Finding 6 — the code that depends on
   `langchain-text-splitters` and `rapidfuzz` was written and, at some point,
   actually run (the Unit 2 results needed `rapidfuzz`'s `token_set_ratio` to
   be produced), but nothing captured that dependency for the next person —
   or the next `pip install -r requirements.txt` — to pick up.

#### Milestone 2 — Write acceptance criteria

**The idea.** Commit to a measurable definition of "working" in `criteria.md`
and five specific test questions in `questions.py` *before* seeing any
results, so that Unit 2's verdicts can't be written to match whatever the
system happens to produce. The failure mode this avoids: grading your own
system against a standard you invent after seeing it pass.

**Where the answers went.** This milestone's work is not cleanly isolated to
one commit — it is interleaved with Milestone 3's chunker work in the commit
history, which is reported plainly here rather than forced into a tidier
shape: `3c4ab39` ("Updated split_documents... used in app.py to chunk
better") changed `criteria.md` by 12 insertions/26 deletions *in the same
commit* as a 74-insertion chunker rewrite; `df834d5` ("questions.py update on
5 Q&As for Corpora 'campus_life'...") changed `questions.py` by 6/6; `c3e6a93`
("Update README with Unit 1 info") touched `criteria.md` by 1/1 alongside an
85/29 README rewrite; `29d93dd` ("Made Target 4 in criteria.md more
specific") changed `criteria.md` by 3/3. All four commits are 2026-09-23.

**What changed and why.** `criteria.md` now holds five criteria (reproduced
in full below). Criteria 1–3 were provided by the course; criteria 4 and 5
were the student's own. Criterion 4 ("at least 80% of sampled chunks...
complete sentences") was revised once, per commit `29d93dd`, to be more
specific than an earlier draft — consistent with the brief's own guidance
that a criterion should name something countable.

| # | Criterion | Target | Provided or authored |
|---|---|---|---|
| 1 | Retrieved chunks contain the answer | 4 of 5 test questions | Provided |
| 2 | Every answer names a source | 5 of 5 | Provided |
| 3 | Relevance gate stops out-of-corpus questions | 4 of 5 | Provided |

#### Milestone 3 — Diagnose every miss

**The idea.** For the one criterion called MISSED, identify which of the
five pipeline stages (loading → chunking → embedding → retrieval →
generation) caused it, and the actual mechanism — not just which stage.

**Where the answers went.** `5ca14dc` (2026-09-29, "README.md Unit 2
Diagnoses," 23/17 on `README.md`).

**What changed and why.** The diagnosis correctly identifies the failure as
belonging to none of the five pipeline stages named in the brief — it
locates the problem in the *test harness* (`scorer.py::judge`) instead, a
sixth location the five-stage model doesn't name. The mechanism, quoted
directly from the (then-current) `judge()`:

```python
def judge(question, expects, answer, results) -> bool:
    return expects.lower().strip() in answer.lower()
```

This requires the entire `expects` string to appear verbatim, in order,
inside the answer. For the health-center question, `expects` was `"In
health_center.txt, walk-in hours are from 8am to 11am."`, while the model's
real answer was `"The walk-in hours at the health center are 8am to 11am
(from health_center.txt)."` — factually identical, correctly sourced, and
still a `False` from `judge()`, because the citation moved from the front of
the string to the back.

**Rejected alternatives** — none presented at the diagnosis stage; this
milestone is analysis, not a fix (the fix, and its alternatives, is
Milestone 4 below).

#### Milestone 4 — Fix one thing and measure it

**The idea.** Make exactly one change the diagnosis points at, then re-run
the full test the same way, so the before/after comparison isolates that one
change's effect.

**Where the answers went.** `61a7a89` (2026-09-29, "Fixed scorer.py to have
higher semantic evaluation accuracy detection") changed `scorer.py` by 19/4
and created `results/run_2026-09-29_1738_before.md` (193 insertions) — later
deleted by `cfdabd9` ("file cleanup," 0/193 on that same file). `0d5dc95`
(2026-09-29, "Retest run_eval.py... Completed README for Unit 2") created the
file that actually holds the "after" evidence,
`results/run_2026-09-29_1810_before.md` (228 insertions) — mislabeled per
Section 5, Finding 7.

**What changed and why.** `scorer.py::judge` was rewritten from an exact,
ordered substring check to `rapidfuzz.fuzz.token_set_ratio`, which compares
the *set* of word tokens in both strings regardless of order or position,
with a 75% similarity cutoff:

```python
SIMILARITY_CUTOFF = 75
score = fuzz.token_set_ratio(expected.casefold(), response.casefold())
return score >= SIMILARITY_CUTOFF
```

This directly targets Milestone 3's diagnosis: citation *position* no longer
affects the score, since `token_set_ratio` ignores order.

**Rejected alternatives**, as recorded in `scorer.py`'s own comments —
genuinely three options were considered, and the middle one was tried and
revised:

| Approach | Why rejected or revised |
|---|---|
| LLM-as-a-judge (send question/expects/answer to Gemini, ask for True/False) | Present in `scorer.py` as commented-out code; rejected for cost — an extra model call per scored answer, against a rate-limited free tier |
| `fuzz.partial_ratio` (first attempt) | Tried, then replaced: it scores on the best *contiguous* character window, which still penalizes a citation moved from the front of the sentence to the back — exactly the failure mode being fixed |
| `fuzz.token_set_ratio` (final choice) | Compares token sets, not contiguous windows — insensitive to citation position, kept as the simplest option that actually fixes the diagnosed mechanism |

**Real output — after the fix**, from `results/run_2026-09-29_1810_before.md`
(the file Finding 7 identifies as mislabeled "before"):

| Criterion | Target | Run 1 | Run 2 | Run 3 |
|---|---|---|---|---|
| 5. In-scope questions pass | 5 of 5 | 2/5 | 4/5 | 2/5 |

Per-question, from the same file's table:

| Question | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| Writing-intensive requirements | fail | fail | fail |
| Health center hours | fail | pass | fail |
| Max work hours | pass | pass | pass |
| CS 210 hours | fail | pass | fail |
| North Kitchen meal cost | pass | pass | pass |

**Comparison — before vs. after**:

| | Before (`run_2026-09-28_1724_before.md`) | After (`run_2026-09-29_1810_before.md`) |
|---|---|---|
| Run 1 | 0/5 | 2/5 |
| Run 2 | 0/5 | 4/5 |
| Run 3 | 0/5 | 2/5 |
| Target | 5/5 | 5/5 |
| Verdict | MISSED | still MISSED |

**Did it help?** Yes, partially, and this is stated plainly rather than
rounded up to a success: the fix moved two questions (max work hours, North
Kitchen cost) from failing every run to passing every run, by removing the
citation-position penalty. It did not reach 5/5 on any run. The
writing-intensive-requirements question failed all three runs even after the
fix — `README.md:514` attributes this to the model additionally reformatting
the citation as a markdown code span in some generations, which still
depresses the token-overlap score. The health-center and CS-210 questions
became inconsistent (pass on Run 2, fail on Runs 1 and 3) rather than
reliably fixed, meaning the new scorer is less broken but still sensitive to
exactly how much the model's wording happens to vary between generations.

**What this means for the next milestone.** None — Milestone 4 is the last
milestone; "What's Still Broken" (below) carries its unresolved part forward
in writing rather than in further pipeline work.

**Terms introduced.** Token-set similarity, exact-substring matching (see
Section 3 glossary entry for "Judge").

**Milestone summary.** True now: one change was made, measured against the
same five questions and the same run format as the "before" measurement, and
the comparison is reported honestly including its partial failure. Not
resolved: Criterion 5 remains MISSED; this is stated in `README.md`'s own
"What's Still Broken" section rather than hidden.

**Lessons taught.**
1. A fix that targets the diagnosed mechanism precisely can still only
   partially work, because the mechanism wasn't the only source of variance
   — model wording itself varies run to run, which a lexical scorer of any
   kind remains sensitive to.
2. "Did it help?" has to be answerable even when the answer is "yes, but not
   enough" — rounding 2/5-4/5-2/5 up to "fixed" would have hidden exactly the
   information Milestone 3's next iteration would need.
3. Trying the obviously-related option first (`partial_ratio`) and rejecting
   it after testing, rather than reasoning it out in advance, is itself
   useful evidence — it ruled out "any fuzzy matcher works" and pinned the
   requirement down to "order-insensitive, specifically."

- [TRUE] Exactly one change was made (the scorer's matching function).
- [TRUE] The full test was re-run in the same format (3 runs × 5 questions).
- [TRUE] Both results are reported side by side, including that the target

- [FALSE] An "after" file correctly labeled as such — the real after-data
